# 食事ヒアリング統合（架空データ専用）

## 構成と境界
Cloudflare Pagesの構成は npm run build / dist。ルートfunctions/とserver/がAPIを担当する。
静的試作をそのまま上書きせず、質問モデルとUIを本体のゲスト画面に組み込んだ。
確認項目1〜7の本文・条件は変更しない。備考にはその他のご要望、食事情報は下の食事ヒアリングに入力する。

## API
- GET /api/guest/meal: セッションの予約・案内版の回答と状態。
- PUT /api/guest/meal: version / expectedRevision / answers / demoDate / consent。
- GET /api/admin/reservations/:id/meal: 所属施設のスタッフだけが閲覧。
- DELETE 同URL: owner限定。削除監査に回答本文を入れない。
ゲストのCSRF・Originチェックと管理者の認証・施設権限・CSRFは既存経路を再利用する。
保存前に質問の回答漏れ、選択値、未知のキー、文字数、同意、デモ期限を検証する。申告は対応承認にならない。
保存失敗時は完了表示しない。再送時の競合は409にして再読込を案内する。

## デモと保持
property.demo=1のみ。実健康情報は禁止。実メール・通知を追加していない。
期限は宿泊4日前の暦日いっぱい（仮）。現在日はデモ用に変更可能であり、実運用の締切制御ではない。
回答は予約・施設・案内版別に保存。案内版が変われば新しい回答が必要。
保存から7日で参照対象外、同予約の次回アクセス時に期限切れデータを削除。
自動定期削除は未設定。ローカル保守で一括消去する場合のみ以下を使用する（公開DBでは実行しない）：

```sql
DELETE FROM meal_response WHERE expires_at <= strftime('%Y-%m-%dT%H:%M:%fZ','now');
```

本運用の同意・保持期間・削除窓口・施設規定・英文は未承認。認証/DB/課金/公開設定は行っていない。
宿側デモでのカテゴリ判断はブラウザ内だけであり、対応承認のワークフローではない。
